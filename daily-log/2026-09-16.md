## 💡 Key takeaways (in my own words)

1. **The four mechanisms sit on a coupling spectrum:** in-process tool (lightest) → CLI → MCP server → agent-to-agent (heaviest). **Pick the lightest one that meets the need** — every step right adds a boundary to deploy, version, secure, and debug.

2. **MCP's whole argument is N×M → N+M.** Three hosts × three systems = nine bespoke connectors; with MCP it's three clients plus three servers. **No reuse across hosts or teams → no payoff** — just a process boundary and a schema round-trip you didn't need.

3. **Decide on three axes:** *reuse* (how many hosts/teams consume it → MCP), *ownership* (another team runs it as its own agent → agent-to-agent), *contract* (need typed inputs, typed results, and error semantics → an API or MCP rather than scraping CLI output).

4. **Each mechanism moves the risk rather than removing it.** Remote MCP → you own auth (OAuth), tenancy, and treating tool results as untrusted input. CLI → the agent has a shell; blast radius needs an allowlist and sandboxing. Agent-to-agent → you depend on another team's agent's behaviour, versioning, and uptime. Direct tool → the risk is in your own code, under your own controls.

5. **The decision sequence:** (1) reused across more than one host or team? → MCP. (2) owned and run by another team as an autonomous agent? → agent-to-agent. (3) a trusted CLI already exists and the agent runs in a shell? → CLI, with an allowlist. (4) otherwise → a direct tool, in-process.
