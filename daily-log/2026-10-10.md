## 💡 Key takeaways (in my own words)

1. **A tool description is a contract, not documentation.** Five parts: a **specific non-colliding name**; a description saying what it does, **when to use it, and when *not* to** (pointing at the right alternative); a **schema** with descriptive names, enums over free strings, stated defaults and units; the **return shape**, so Claude can plan its next step; and **actionable error semantics** that distinguish *empty result* from *failure*.

2. **Say when to call it.** A description that only states what a tool does under-triggers. "Call this when the user asks about current prices or recent events" measurably lifts should-call rate over "Searches for prices." Trigger conditions belong in the tool's own description, not only the system prompt.

3. **Under-description is the more common defect than over-description.** Vague one-liners and undocumented parameters are the usual failure. The thing to *remove* from a description is behavioural steering and worked examples, not contract detail.

4. **Capability bloat is a real architecture smell.** Too many tools, or overlapping ones, degrade selection accuracy *and* burn context on every single request. Fixes: consolidate overlapping tools, scope the tool set **per agent or per task** rather than per system, and prefer a few well-described tools over many thin ones.

5. **Progressive discovery vs. monolithic context.** Monolithic loads everything up front — simple and predictable, but expensive, and accuracy *degrades* as irrelevant material crowds the window. Progressive exposes an index and lets the agent pull detail on demand (list → describe → fetch) — cheaper, scales to large surfaces, costs a round trip, and depends entirely on good descriptions. **Rule of thumb: small, stable, always-needed → monolithic (and cache it). Large, sparse, or varying per request → progressive.**
